# BookConverter — 開発・移植計画

> Status: Planning / 2026-10-20  
> 対象: Windows向け漫画・画像主体EPUB → CBZ / AVIF変換アプリ  
> リポジトリ: `irorisan/BookConverter`  
> 原本: 添付 `Convert-Manga-AVIF-Quality70-EPUB-Standalone.zip`（`Convert-Manga.ps1` 1,052行、`Convert-Manga-Epub.ps1` 234行、`Convert-Manga.bat` 27行、および README。静的確認のみ）

## 0. 決定事項

- **技術スタック**: **Tauri 2 + React + TypeScript + Tailwind CSS + shadcn/ui + Rust**。
- Windows 11を主対象。モダンでシンプルなネイティブウィンドウのデスクトップアプリとする。ダーク/ライトモード対応。古いWinForms風UIは採用しない。
- フロントエンドは**表示と操作だけ**。ファイル解析、アーカイブ、変換キュー、品質探索、出力検証は**Rust側**が担当する。
- 初期エンコーダは現行版と同じ `avifenc` を外部プロセスとして利用。将来の `libavif` 直接連携は**計測結果を見てから**判断する。Rust化そのものではAVIF圧縮計算は速くならない。
- PowerShell / BATへの依存は最終版で廃止。**移植途中の実行・結果比較には現行版を基準実装として使用**してよい。
- まず既存挙動を再現し、最適化や仕様変更は**別段階・別PR**とする。
- この文書は**実装計画**。現時点でアプリ・CI・自動テストが完成しているという意味ではない。

### 開発ルール（全Phase共通）

開発時はリポジトリルートの [AGENTS.md](../AGENTS.md) を参照し、**資料ファースト → TDD → 最小実装 → 不要コード・資料矛盾の確認**の順に進める。

1. **資料を先に更新**：要求・設計・影響範囲・期待動作を `DOCS/` に明記し、既存資料の重複・矛盾・古い情報を解消してから実装へ進む。
2. **実装より先にテスト**：新仕様・不具合に対応する失敗テスト（Red）を作成する。UI/外部ツールの都合上テストできない箇所は、代替の確認方法と理由をPRに記載する。
3. **最小実装**：テストを通す最小の実装（Green）と必要なリファクタリングに留め、KISS/YAGNIを優先する。
4. **最終整合確認**：不要コード・未使用依存・古い設定・資料の矛盾を取り除き、最新HEADの `quality` 成功を確認する。

このプロジェクトは開発中の内部利用向けアプリであり、**未公開・未確定の過去実装を維持するための後方互換レイヤーやデータ移行コードは追加しない**。目指す設計に直接置き換える。一方、表に定義した**合意済みの製品仕様と元ファイル保護**は守る。変更する場合は先に仕様書を更新し、対応するテストを変更する。ここでいう「既存挙動の再現」は、不要な旧API互換ではなく、合意された変換結果の仕様を指す。

## 1. 成果物と非目標

### MVPで提供するもの

1. ファイル/フォルダを複数ドラッグ＆ドロップ、ファイル選択でも追加、変換前の一覧確認。
2. 巻物・雑誌/単巻の判定、名称編集、出力予定名のプレビュー、競合警告。
3. `ZIP / CBZ / RAR / EPUB / 画像フォルダ` を入力、`CBZ` を出力。
4. 60MiB判定、自動AVIF品質探索、並列変換、進捗、停止/キャンセル、成功/スキップ/失敗の結果一覧。
5. 元データ保護、既存出力の非上書き、途中失敗時の後片付け、ページ順・解像度の維持。
6. Windows用のインストーラー/配布ビルド（Tauri 2）とユーザー向けREADME。

### 初期対象外

- 本文テキスト中心のEPUB、DRM解除、OCR、画像編集/リサイズ/超解像、WebPへの書き出し。
- クラウド同期、アカウント、Kavitaサーバーへの直接アップロード、外部作品メタデータの自動取得。
- AVIFのデコード/エンコードライブラリを最初から全面自作すること。
- 画質・圧縮率の**保証**。「70MiB以内に必ずなる」という表示もしない。

## 2. 現行版の互換仕様（ソース/READMEで確認済み）

| 分野 | 維持する挙動 |
|---|---|
| 入力 | `.zip / .cbz / .rar / .epub` と画像を含むフォルダ。複数一括入力可能 |
| 読み込み階層 | 投入した巻フォルダを優先。作品/ライブラリのコンテナフォルダは子、さらに孫まで探索。出力フォルダを再投入対象にしない |
| 画像 | JPG/JPEG、PNG、WebP、GIF、BMP、AVIFを取り込み。**60MiB超でAVIF化するのはJPG/JPEG/PNG/WebPのみ**。その他は原形を保持 |
| 巻識別 | `15巻`、`v15`、`vol.15`、`（１５）`、`作品名（１５） - 著者名`、小数・英字枝番などを認識。数字/枝番だけを正規化し作品名文字列は維持 |
| 巻名 | `v01`、`v15`、`v100`。枝番 `b/B` **だけ**出力名から削除（`v100b→v100`）。`a` 等は残す。結果名例 `作品名 v50.cbz` |
| シリーズ名 | 巻数ありを含む一括入力時に1回指定。現行版は同一バッチ内のシリーズ巻すべてに適用する（複数シリーズ混在は警告）。巻数なしには適用しない |
| 雑誌/単巻 | 巻数なしファイルは元のベース名で `タイトル.cbz`。画像フォルダは直下に画像があり、サブフォルダ/アーカイブ子がない場合だけ単巻扱い |
| 出力先 | **各入力の親（ファイルなら同階層）の `avif変換cbz/`**。元ファイルと同じ階層にCBZを直接置かない |
| 入力サイズ `<= 60MiB` | AVIF再圧縮しない。CBZ入力はファイルを**バイト単位でそのままコピー**。他形式はCBZへ詰め直し（EPUBはページ番号付与） |
| 入力サイズ `> 60MiB` | JPEG/PNG/WebPをAVIF化し、完成CBZが**70MiB以下を目指す** |
| 品質探索 | `Q30〜Q95`。代表**最大12ページ**を均等選択、**最大5回**の二分探索。ZIP管理情報の概算を引き、内部見積り目標 **68MiB**（上限70MiBから2MiB安全余裕） |
| 再利用・再試行 | 採用品質でエンコード済みの代表ページは本番へ再利用。実際のサイズ超過時だけ品質を下げて**全体最大3回**。追加の代表ページ探索はしない |
| 上限超過時 | 3回でも70MiBを達成できない場合、現行版は**試した中で最小の結果を警告付きで保存**。MVPは同じ挙動を維持し、UIに超過を明確に表示 |
| エンコード | `avifenc -q <選択Q> -s 6 -j 1`。画像単位の並列は論理CPU数の半分（最低1、**自動最大8**）、手動**1〜16** |
| WebP入力 | `dwebp` でPNGへ可逆展開してから `avifenc`。変換対象になったときだけ使用 |
| ページ順 | 通常の入力は画像名の自然順（数字の数値順を意識）。EPUBはspineの読書順。並列処理完了順に左右されない |
| CBZ書き込み | ZIPの**Store（無圧縮）**。画像枚数・ファイル名・サイズを検証後、一時CBZから最終パスへ移動 |
| 衝突・原本 | 同名出力があればスキップ、同一バッチで正規化後に出力名が衝突しても警告・スキップ。元入力は削除も上書きもしない |

**注意**: 現行READMEにも「Windows実機での変換は未検証」と明記されている。上表は**仕様/ソースから読み取れる動作**であり、実機で保証された結果ではない。実装前にスモークテストでベースラインを取得する。

### EPUB固有仕様

- `META-INF/container.xml` → OPF → manifest / spine → XHTML/SVG内の `img` / `image` / `object` を解析し、読書順を維持する。
- 画像を `001.jpg`、`002.png` … の連番へ。ページ数に応じて必要な桁数を確保。
- 表紙指定画像が本文に含まれない場合、先頭に**一度だけ**追加。
- 外部URL、EPUBルートを超える相対パスを拒否。ZIP全体でなく必要な画像を専用作業フォルダへ展開。
- 非対応: DRM、テキスト主体、CSS背景画像のみ、純粋なSVGベクターのみ。読書ページに有効画像がない等の不完全なEPUBは**部分的CBZを保存せず失敗**。
- EPUB単独処理にはWinRARは不要。現行版では非EPUBアーカイブ入力にWinRARが必要。

### 移植時に特に検証したい例外

- `v100.cbz` と `v100b.cbz` を同時投入すると、正規化後は同じ `v100.cbz`。**通常巻優先**、枝番b側スキップをテスト。
- `v03a` は `v03a`、`v03b` は `v03` のまま。小数巻・全角数字・日本語・著者クレジット。
- 大小文字違いの画像名、`001.jpg` と `001.webp` のAVIF化後の衝突、同名画像が異なるサブフォルダにある場合は、**黙って上書きせず失敗**。
- `60MiB` ちょうどは再圧縮なし、**1バイト超**で再圧縮対象。1MiBは1,048,576バイト。
- 画像主体EPUBの表紙重複、参照パス・URLエンコード、XML/アーカイブの異常、読書順。
- 70MiBに収まらないケースは**警告付き成功（上限超過ステータス）**として明示すること。

## 3. アーキテクチャ

```text
┌──────────────────────────────────────────┐
│ Tauri 2 / React + TypeScript             │
│ Tailwind CSS / shadcn/ui                 │
│ Dropzone • Queue • Settings • Progress  │
└─────────────────┬────────────────────────┘
                  │ Tauri typed commands / events
┌─────────────────▼────────────────────────┐
│ Rust application                         │
│  input scan → naming/preview → job queue │
│  archive/EPUB reader → ordered pages     │
│  sample/quality selection → AVIF workers │
│  CBZ writer → validation → atomic publish│
└─────────────────┬────────────────────────┘
                  │ external executable (MVP)
         avifenc / dwebp
```

**責務分離**
- React: 入力と結果の表示、ユーザー操作、進捗イベント購読。ファイルシステムの直接アクセス・任意コマンド実行は禁止。
- Rust `domain`: 巻数パーサー、出力名/安全性検証、容量判定、品質探索ロジック。可能な限り純粋関数化。
- Rust `io`: アーカイブ/EPUB、テンポラリ、CBZ書き込み、ファイルシステム検証。
- Rust `engine`: 外部エンコーダー起動・終了コード/出力検証・並列上限制御・キャンセル・試算画像キャッシュ。
- Rust `app`: Tauri commands とイベント、ジョブ/設定の保持。1ジョブ＝1巻、バッチ＝複数ジョブ。
- サードパーティーツールはアプリ管理ディレクトリに同梱するか初回取得とするかを**ライセンス・署名・更新・オフライン動作の検証後に決定**。配布ZIPに含まれるバイナリを無検証でGitに登録しない。

### データモデルの案

- `InputItem`: sourcePath, type, detectedTitle, volume?, isStandalone, parentOutputDir。
- `PlannedOutput`: sourceId, normalizedOutputName, destination, collision?, conversionRequired?。
- `ConversionJob`: jobId, sourceId, status (`queued | running | cancelling | cancelled | succeeded | skipped | failed | oversized`), progress, sourceBytes?, resultBytes?, quality?, reason?。
- `Settings`: workers (`auto` または 1–16)、theme、outputFolderName（初期値固定）、エンコーダー速度（MVPでは固定）。
- `ProgressEvent`: jobId, stage (`scan | extract | sample | encode | pack | verify | finish`), completed, total, message。
- イベントは順不同・多重発行を考慮。画面はjobIdで状態を更新し、最終状態への遷移を単方向に保つ。

### ファイル安全性/キャンセル

1. ユーザー入力はローカルパスのみを受け付け、展開時に `../`・絶対パス・シンボリックリンク・不正エントリを検証。アーカイブ爆弾対策として展開サイズ/エントリ数の上限を設計・検証する。
2. 最終出力は**同じ保存先ファイルシステム内の一時ファイル**から公開。公開直前まで元データと既存CBZに手を加えない。
3. 既存出力は上書きせずスキップ。並列ジョブ間の出力パス予約とファイル作成競合を保護。
4. キャンセル時は新規エンコード投入を停止し、実行中の子プロセスを適切に終了、テンポラリのみ削除。元入力・既存出力は不変。
5. エンコーダー終了コードだけでなくAVIFヘッダー等の生成物を検証。ZIPエントリ数・順序・名前・サイズも検証。
6. ユーザーへのエラーは日本語で簡潔に、詳細ログには処理段階・原因・子プロセス終了コードを残す。個人のフルパスの外部送信はしない。

## 4. GUI/UX

**デザイン方針**: 余白を活かしたミニマルな画面、Windows 11に馴染む角丸。明るいライトテーマ/落ち着いたダークテーマ。派手な装飾・古いダイアログ中心のUIを避ける。

**画面構成**
- **メイン**: ファイル/フォルダのドロップ領域と追加ボタン、変換待ち一覧（タイトル・巻・入力種別・入力容量・出力名・状態）、削除/全消去。
- **設定**: 並列数（自動/1〜16）、保存先ルールの説明、テーマ、エンコーダーの所在/診断。品質Qは原則自動（30〜95）を基本とする。
- **進捗**: バッチ全体と巻別の件数/ページ数/段階を表示、キャンセル。**ETAは計測根拠がない限り表示しない**。
- **結果**: 成功/スキップ/失敗/上限超過、入力・出力MiBと削減率、品質Q、出力フォルダを開く、失敗理由/ログ。
- 出力名は変換開始前に明示。巻物が複数作品にまたがるときは**一括同名化される現行挙動を警告**する。シリーズ別入力・編集の改善は後続提案として切り離す。
- キーボード操作、スクリーンリーダー対応のラベル、明瞭なエラー/警告色、長い日本語パスの省略表示＋詳細確認。

## 6. フェーズ別の実施順序・PR境界

| Phase | 主な作業 | 受け入れ条件 |
|---|---|---|
| **0: 基準化** | 現行スクリプトとREADMEを分析し、合成入力セットと期待結果（巻数・出力名・EPUB順・閾値）を固定。Windows実機で基準動作を記録 | 再現手順、差分比較表、失敗条件が文書化される |
| **1: 足場と品質ゲート** | Tauri 2/React/TS/Tailwind/shadcn/ui導入、Rustモジュールの枠、最小権限、Windowsビルド、`quality` CI | ローカルビルドとPR CIの**`quality`成功** |
| **2: 入力・命名・出力計画** | ドロップ/選択、深さ制限付き走査、巻数パーサー、単巻検出、衝突処理、予定名一覧 | 日本語・全角・枝番・複数巻の自動テスト成功 |
| **3: アーカイブ/EPUB/CBZ** | ZIP/CBZ/RAR/フォルダ、EPUB spine解析、自然順、60MiB以下処理、CBZ Store/検証 | 元データ不変、各形式の順序・表紙・内容を確認 |
| **4: AVIF変換エンジン** | avifenc/dwebp、ジョブ/並列数、最大12×5の試算、キャッシュ再利用、最大3回リトライ | 容量境界・上限超過・AVIF検証・キャンセルを確認 |
| **5: GUI仕上げ** | 進捗/結果/ログ、テーマ・アクセシビリティ、詳細エラー、同名警告 | UIから全操作可能、フリーズしない、迷わず再試行できる |
| **6: 配布・検証** | Windowsインストーラー、依存ツール/ライセンス、WebView2前提、E2Eスモーク、Kavita/Mihon目視確認 | クリーン環境で動作、代表形式でページ抜けなし、`quality`成功 |

- 原則**Phaseごとに小さな独立PR**。依存がある場合もマージ順・テスト対象を明記。
- `quality` が最新コミットに対して**成功**する前は「実装完了」と報告しない。未設定・pending・failedはそのまま明示。
- 移植後の高速化（`-s` 値比較、I/O削減、`libavif`直接連携、品質探索ロジック変更）は**別PRでベンチマーク根拠を付ける**。
- 工数は参考として段階移植約4〜8開発日、より広い完全移植・配布品質の仕上げは2〜4週間程度を想定。ただしテスト素材、Windows環境、依存ツールの扱いで変動。

## 7. テストとCI設計

### テスト層

- **Rust単体**: 巻数の正規化、自然順、60MiB境界、サイズ推定、品質候補選択、同名競合、EPUBパスのサニタイズ。
- **Rust統合**: 小規模合成ZIP/CBZ/RAR/EPUB、重複名、破損アーカイブ、文字コード、日本語/長いパス、表紙、画像を含まない巻、失敗時の一時ファイル削除。
- **変換統合**: サンプル画像でavifenc/dwebpの起動・出力ヘッダー・画素寸法・順序・ZIP Storeを検証。容量閾値はファイルサイズだけでなくモックを使って高速に網羅する。
- **UI**: ドロップ、設定、確認、状態遷移、停止、警告、出力フォルダ参照を確認。
- **Windows実機E2E**: クリーン環境、AVIF依存ツール、EPUB読書順、1巻/複数巻の変換結果、Kavita/Mihon表示。
- **比較**: 同一入力について現行版とRust版の**名前・ページ順・解像度・枚数・容量・Q・警告/スキップ**を比較。エンコーダーの非決定性・バージョン差があるため生成バイト列の完全一致は要求しない。

### GitHub Actions `quality`（Phase 1で作成）

- Windows runnerを含むワークフロー。`npm ci`、TypeScript型チェック、ESLint、フロントエンドテスト、`cargo fmt --check`、`cargo clippy -- -D warnings`、`cargo test`、Tauriアプリビルドを段階的に導入。
- ドキュメント検査（Markdown内部リンク・参照先など）は任意で追加。
- PRの最新HEAD SHAのチェック結果で判定。必要なCIが未設定なら**検証済み扱いにしない**。
- サンプル画像は再配布権を持つ合成データを使用し、実漫画・個人の購入書籍をリポジトリにコミットしない。

## 8. リスクと設計上の決めどころ

1. **エンコーダー**: WindowsでのAVIFバイナリ配置、対応入力、ライセンス/再配布・署名・セキュリティ更新。実装開始時に採用方法を確定する。
2. **RAR**: 初期段階では既存WinRAR利用も可能だが、最終版でWinRAR必須を残すか代替デコーダーを選ぶかは機能・配布条件を調べて決める（未決定）。
3. **EPUB**: EPUB2/3のマニフェスト・spineの多様性、パス、表紙、XMLの安全性、暗号化/非画像ページへのフェイルクローズを最優先。
4. **70MiBの実際**: 元スクリプトは上限を超えても最小候補を出す。保証文言ではなく状態表示で扱い、厳格上限モードは将来の仕様相談とする。
5. **CPU/ディスク負荷**: `-j 1` + ページごと最大8並列が初期設定。メモリ、SSD/HDD、熱、負荷に応じて上限の実測評価が必要。
6. **ユーザーデータ保護**: アーカイブパストラバーサル、ZIP爆弾、シンボリックリンク、キャンセル途中の孤児プロセス、既存ファイル上書き/競合。
7. **デザイン/パッケージ**: shadcn/uiはコンポーネント実装を取り込む方式。WebView2依存・Windows配布サイズ・アンチウイルス誤検知を配布前に確認。
